## Как пользоваться этим файлом

- **P0** — риск краша/потери данных/нарушения безопасности/критичный UX-инвариант.

- **P2** — косметика/упрощения/снижение шума, можно после релиза.

Формат пункта:
- **ID**
- **Где**: файл / класс / метод / фрагмент
- **Проблема**
- **Риск**
- **Что сделать**
- **Как проверить**

## P0 (критично)

### TD-001 (P0)
- **Статус:** ✅ Закрыто в R1.5.2 (null-safe итерация `DanglingMetaAttachmentIds`).
- **Где:** `AttachmentsOrphanCleanupService.cs`, метод диагностики orphan index, цикл `foreach (var id in idx.DanglingMetaAttachmentIds)`.
- **Проблема:** `DanglingMetaAttachmentIds` может быть `null`, при этом используется без `??`.
- **Риск:** краш/срыв orphan-cleanup диагностики; в худшем случае пропуск важных диагностик и некорректное поведение cleanup.
- **Что сделать:** заменить на `foreach (var id in idx.DanglingMetaAttachmentIds ?? Enumerable.Empty<Guid>())` (или аналогично), пройтись по всем коллекциям из `AttachmentReferenceIndex`, где возможен `null`.
- **Как проверить:** принудительно смоделировать ситуацию, когда `DanglingMetaAttachmentIds == null` (или запуск с vault без вложений) → убедиться, что cleanup не падает и пишет корректные маркеры в `diagnostic.log`.

### TD-002 (P0)
- **Статус:** ✅ Закрыто в R1.5.2 (null-safe доступ к `Grid` при очистке на Lock).
- **Где:** `MainWindow.xaml.cs`, `ClearSensitiveUiForLock()`.
- **Проблема:** обращения `Grid.UnselectAll()` и `Grid.SelectedItem = null` без `?.` (обёрнуто в `try/catch`, но это не устраняет предупреждение и может скрывать реальные ошибки).
- **Риск:** потенциальный `NullReferenceException` при нестандартных сценариях жизненного цикла окна (ранний lock/закрытие/ошибка инициализации), скрываемый пустым `catch`.
- **Что сделать:** заменить на `Grid?.UnselectAll(); Grid?.SelectedItems?.Clear(); Grid?.SetCurrentValue(...);` и убрать лишние пустые `catch` (оставить минимально безопасные).
- **Как проверить:** несколько циклов `Lock → Unlock` + закрытие/открытие приложения в разных состояниях (есть/нет выделения), убедиться что UX-инварианты и выделение работают.

### TD-003 (P0)
- **Статус:** ✅ Закрыто в R1.5.2 (null-safe синхронизация selection при restore по double-click; helper перенесён).
- **Где:** `MainWindow.xaml.cs`, `TryRestoreFromTrashByDoubleClick()`.
- **Проблема:** `Grid.SelectedItems.Add(entry)` и `Grid.SelectedItem = entry` без `?.`.
- **Риск:** потенциальный NRE; также риск рассинхронизации `SelectedEntries` ↔ `Grid.SelectedItems`.
- **Что сделать:** безопасная синхронизация через `Grid?....` + единый helper-метод “SetSingleSelection(entry)”, который аккуратно обновляет и Grid и `SelectedEntries`.
- **Как проверить:** режим корзины → double-click restore → убедиться что восстанавливается ровно 1 элемент, selection очищается корректно, ничего не падает.

### TD-004 (P0)
- **Статус:** ✅ Закрыто в R1.5.3.1 (атомарная запись temp+replace + .bak).
- **Где:** `SettingsStore.cs`, сохранение `settings.json`.
- **Проблема:** `File.WriteAllText(SettingsPath, ...)` без атомарной записи (temp+replace).
- **Риск:** повреждение `settings.json` при внезапном завершении/выключении питания в момент записи → возможна потеря настроек, нестабильный старт.
- **Что сделать:** писать во временный файл в той же папке и делать `File.Replace`/`File.Move` по аналогии с `VaultStore.Save`.
- **Как проверить:** имитация прерывания (kill процесса) в момент сохранения настроек (например, изменять setting и сразу закрыть) → после запуска settings корректно читаются/восстанавливаются (fallback).

### TD-005 (P0)
- **Статус:** 🟡 Частично в R1.5.2 (минимальная диагностика swap директории вложений и orphan-enumeration).
- **Где:** множество файлов, массовое использование `catch { }` в критических ветках (backup/restore/cleanup/IO).
- **Проблема:** пустые `catch` скрывают исключения и затрудняют диагностику; часть веток должна как минимум писать в `diagnostic.log`.
- **Риск:** тихие сбои операций (копирование вложений в backup, restore, self-heal), которые пользователь не сможет объяснить.
- **Что сделать:** в критических местах заменить `catch { }` на `catch (Exception ex) { DiagnosticsLog.AppendLine(TAG, ...ex.GetType().Name...); }` без выброса наружу.
- **Как проверить:** сымитировать ошибки IO (отсутствие прав, блокировка файла) → убедиться, что приложение не падает, но пишет понятный TAG.

## P1 (важно)

### TD-006 (P1)
- **Статус:** ✅ Закрыто в R1.5.3.2 (логирование через DiagnosticsLog).
- **Где:** `VaultIoGate.cs`.
- **Проблема:** собственная реализация логирования (путь/формат) дублирует `DiagnosticsLog`.
- **Риск:** разные форматы логов, труднее анализировать; риск рассинхронизации путей.
- **Что сделать:** использовать `DiagnosticsLog.AppendLine("IO_GATE_WAIT", ...)` вместо прямого `File.AppendAllText`.
- **Как проверить:** смоделировать конкуренцию IO (backup + save) → увидеть `IO_GATE_WAIT` в `diagnostic.log`.

### TD-007 (P1)
- **Где:** `MainWindow.xaml.cs`, обращения к `Grid.SelectedItems`/`Grid.SelectedItem` в разных местах.
- **Проблема:** много разрозненной логики синхронизации выделения и `SelectedEntries`.
- **Риск:** регрессии multi-select/Ctrl+A/Del/drag&drop при точечных правках.
- **Что сделать:** выделить 2–3 helper-метода: `TryGetSelectedEntries()`, `ClearSelectionSafe()`, `SetSelectionSafe(list)` и везде использовать их.
- **Как проверить:** регресс-чеклист multi-select (мышь/клава), Ctrl+A, Del, drag&drop, “клик в пустоту…” — всё должно работать как раньше.

### TD-008 (P1)
- **Где:** `MainWindow.xaml.cs`, предупреждения nullable по `Grid`.
- **Проблема:** `Grid` (DataGrid) вероятно всегда инициализирован после `InitializeComponent`, но для компилятора остаётся nullable.
- **Риск:** шум предупреждений скрывает реальные проблемы.
- **Что сделать:** выбрать стратегию:
  - (а) сделать локальный non-null accessor `private DataGrid GridNN => Grid ?? throw ...;` и использовать в местах, где по жизненному циклу точно не null,
  - (б) в безопасных местах использовать `?.`,
  - (в) сократить `try/catch` вокруг NRE.
- **Как проверить:** `dotnet build` → снижение числа CS8602 без изменения поведения.

### TD-009 (P1)
- **Статус:** ✅ Закрыто в R1.5.2 (убран дубль закрытия; добавлен локальный helper).
- **Где:** `PasswordGeneratorWindow.xaml.cs`.
- **Проблема:** дублирующая строка `CopyFailedToastPopup.IsOpen = false` (двойной вызов).
- **Риск:** низкий, но это сигнал “копипасты” и усложняет поддержку.

- **Как проверить:** Copy в генераторе → toast OK/Fail показывается и закрывается корректно.

### TD-010 (P1)
- **Статус:** ✅ Закрыто в R1.5.3.3 (SettingsWindow + PasswordGeneratorWindow → PopupToastController; MainWindow уже на PopupToastController с отдельным курсор-якорем).
- **Где:** `SettingsWindow.xaml.cs`, `PasswordGeneratorWindow.xaml.cs`, `MainWindow.xaml.cs`.
- **Проблема:** разные места реализуют toast/таймеры по-разному.
- **Риск:** расхождение UX, дубли, сложнее фиксить баги (как с позиционированием).
- **Что сделать:** постепенно унифицировать через `PopupToastController` (1 контроллер + разные Popup’ы).
- **Как проверить:** копирование/уведомления в разных окнах ведут себя одинаково по таймингу и закрытию.

### TD-011 (P1)
- **Где:** `MainWindow.xaml.cs`, `App.xaml.cs`, другие окна.
- **Проблема:** много `MessageBox.Show` (ошибки/инфо/подтверждения). Для части сценариев это норм, но часть сообщений может вызывать фокус/мигание и ухудшать UX.
- **Риск:** раздражающий UX, возможные побочные эффекты с фокусом (особенно поверх других окон).
- **Что сделать:** инвентаризировать MessageBox по категориям:
  - A) критические подтверждения — оставить,
  - B) “info/copy/не критично” — переводить на toast/popup.
- **Как проверить:** закрытие окон после действий (copy/confirm) без фокуса/миганий; критические confirm остаются модальными.

### TD-012 (P1)
- **Статус:** ✅ Закрыто в R1.5.3.1 (логирование `SETTINGS_LOAD_ERROR` + fallback на `.bak` + auto-heal).
- **Где:** `SettingsStore.cs`.
- **Проблема:** нет защитного fallback при повреждённом `settings.json` (не видно из этого файла, но важно проверить поведение `Load()`).
- **Риск:** невозможность старта/сброс настроек без объяснения.
- **Что сделать:** при JSON parse error — писать `SETTINGS_LOAD_ERROR` в `diagnostic.log` и возвращать дефолты (best-effort).
- **Как проверить:** испортить `settings.json` → приложение стартует с дефолтами, логирует ошибку.

### TD-013 (P1)
- **Где:** `BackupService.cs`.
- **Проблема:** много best-effort операций с пустыми `catch` при работе с файлами (удаления temp/директорий).
- **Риск:** “мусор” в папке backup, накопление временных файлов.
- **Что сделать:** логировать хотя бы тип исключения при частых сбоях, и/или ограничить ретраи/чистку.
- **Как проверить:** запуск backup/restore на диске с ограниченными правами → приложение не падает, но диагностирует.
