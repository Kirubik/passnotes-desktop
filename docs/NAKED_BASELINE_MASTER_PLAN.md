## 1. Главная цель текущего периода

Сохранить по всему WPF-native UI приложения единый naked baseline UI и на его основе безопасно запустить новую дизайн-ветку без визуальных регрессий.

Ключевая цель текущего периода:

- не переделывать baseline заново;
- не смешивать дизайн-ветку с хвостами `0.X`;
- сохранять уже собранный runtime-theme набор и baseline без новых хаотичных визуальных исключений;
- открывать следующий основной блок только по новому явному подтверждению пользователя.

---

## 2. Что считается завершенным и зафиксированным

Подготовительно закрыты и считаются стабильной опорой:

- baseline-база `_230`;
- shared baseline dictionaries;
- hard reset `MainWindow`, `EntryWindow`, `SettingsWindow` и app-owned dialog layer;
- WPF `ContextMenu` / `MenuItem` и popup-menu family (`семейство popup-меню`);
- shared icon token layer (`общий слой токенов иконок`) и миграция основных окон на icon tokens (`токены иконок`);
- предтемизационная дочистка `Этапов 1.25-1.38`, включая toast-family (`семью toast-уведомлений`);
- временная линия хвостов `Этапов 0.1-0.6`.

Эта baseline-линия считается закрытой подготовительной веткой и не должна автоматически оживляться через старую схему `2.1 → 2.2 → 2.3`.

---

## 3. Принципы текущей линии

1. Один контрол — один владелец visual state (`визуального состояния`).
2. Shared baseline всегда важнее локального window-level визуала.
3. Новая дизайн-ветка строится поверх baseline, а не вместо baseline.
4. Любая новая тема сначала проходит через общий runtime-theme scaffold (`каркас runtime-темы`), а не через локальные подмены по окнам.
5. Исторические theme-assets (`theme-артефакты`) не должны считаться живой частью маршрута.
6. Любое новое изменение по умолчанию сначала проверяется на немедленное встраивание в единую baseline-систему проекта.
7. Все пользовательские сценарии и инварианты должны сохраняться.

Если baseline-интеграция в конкретной задаче сейчас рискованна, преждевременна или может повредить стабильности, это нужно явно фиксировать до начала реализации.

## 4. Обязательный охват зафиксированного baseline

В уже собранный общий baseline входят:

- shared baseline dictionaries;
- `MainWindow`;
- `EntryWindow`;
- `SettingsWindow`;
- secondary dialogs (`вторичные диалоги`);
- `DataGrid`, `DataGridRow`, `DataGridCell`, `DataGridColumnHeader`;

- `Button`, `ToggleButton`, `TextBox`, `PasswordBox`, `ComboBox`, `CheckBox`, `TabControl` / `TabItem`;
- context menu / popup / toast / icon token layer (`слой контекстных меню / popup / toast / токенов иконок`).

Это считать действующей технической опорой новой дизайн-ветки `5.X`.

---

## 5. Что не входит в текущий маршрут

Внутрь текущего периода без отдельного подтверждения не входят:

- новые пользовательские темы вне уже зарегистрированного набора `standard` / `light` / `arctic-white` / `midnight-slate` / `amber-circuit`;
- финальная палитра и финальный редизайн;
- новый отдельный pass по live theme switching (`живому переключению темы на лету`);
- широкая дочистка всех legacy-окон (`устаревших окон`) в одном проходе;
- изменение бизнес-логики ради визуала;
- возврат к хвостам `0.X` без отдельного запроса.

### 5.1. Зафиксированная practical theme boundary

Для новой отдельной дизайн-ветки действует следующая граница:

- тема должна покрывать весь app-owned WPF UI;
- WPF `ContextMenu` / `MenuItem` и app-owned dialog layer уже приведены к общему shared-слою;
- tray menu и file/folder dialogs остаются системной внешней границей ОС и не входят в обязательный practical coverage (`практический обязательный охват`).
