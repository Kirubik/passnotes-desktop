# Этап 3 / Подблок 3.1 — полный аудит проекта перед cleanup

Дата фиксации: 2026-03-08 (Europe/Moscow)

## 1. Назначение документа

Этот документ фиксирует полный снимок текущего состояния проекта перед cleanup-линейкой.

Его задача:

- отделить подтвержденный мусор от спорных зон;
- отделить безопасный cleanup от рискованного code health refactor;
- зафиксировать, что можно убирать в `Этапе 3 / Подблоке 3.2`;
- зафиксировать, что должно идти отдельным подблоком `3.3` и дальше;
- не допустить хаотичного удаления файлов и "чисток по ощущению".

Этот документ является рабочим источником истины для cleanup-линии `Этапа 3`.

## 4. Подтвержденный мусор / safe cleanup-кандидаты

Ниже перечислено то, что уже в аудите выглядит подтвержденным и безопасным кандидатом для cleanup без смены логики приложения.

### 4.1. `analysis_frames/`

Статус:

- папка присутствует в корне;
- файлов внутри нет;
- ссылок на нее в проекте не найдено.

Оценка:

- это подтвержденный локальный служебный хвост;
- кандидат на удаление в `Этапе 3 / Подблоке 3.2`.

### 4.2. `.gitignore.txt`

Статус:

- файл есть в корне рядом с `.gitignore`;
- содержимое дублирует `.gitignore`;
- ссылок на `.gitignore.txt` в проекте не найдено.

Оценка:

- это подтвержденный дублирующий артефакт;
- кандидат на удаление в `Этапе 3 / Подблоке 3.2`.

### 4.3. `archives/` не исключен из git-шума

Статус:

- папка `archives/` используется по текущим правилам как хранилище milestone-архивов;
- она не должна становиться частью исходников;
- сейчас она не игнорируется `.gitignore`, поэтому постоянно висит как `?? archives/`.

Оценка:

- это не мусор, но это confirmed cleanup-кандидат по рабочей среде;
- в `Этапе 3 / Подблоке 3.2` логично добавить `archives/` в `.gitignore`, чтобы рабочее дерево оставалось чистым.

### 4.4. `README.md`

Статус:

- файл существует;
- по содержанию он описывает проект как `demo`;
- в нем отсутствует актуальный контекст текущей рабочей линии, архивации, baseline/design-процесса и текущего способа запуска.

Оценка:

- это не мусор на удаление;
- это устаревший документ;
- безопаснее считать его cleanup/актуализацией docs, а не удалением.

## 5. Подтвержденные проблемные зоны, но не safe cleanup

Это не мусор. Это реальные зоны долга, которые нельзя чистить вслепую в том же проходе, что и удаление артефактов.

### 5.1. Монолит `MainWindow.xaml.cs`

Состояние:

- `7133` строк;
- на нем висит большая часть selection, tree, backup/restore, import/export, lock/unlock, attachments и UI orchestration.

Оценка:

- это главный риск сопровождения проекта;
- безопасным удалением это не лечится;
- требует отдельного точечного блока `Этап 3 / Подблок 3.3`, а не `3.2`.

### 5.2. Монолит `EntryWindow.xaml.cs`

Состояние:

- `1938` строк;
- внутри смешаны логика окна, pending attachments, comment window orchestration, clipboard/toast и много best-effort cleanup.

Оценка:

- это второй крупный hotspot;
- безопасный cleanup здесь возможен только точечно;
- серьезная переработка должна идти отдельно.

### 5.3. Массовые `catch { }`

По проекту найдено `392` пустых `catch { }`.

Крупнейшие концентрации:

- `MainWindow.xaml.cs` — `219`
- `EntryWindow.xaml.cs` — `53`
- `BackupService.cs` — `47`
- `SettingsWindow.xaml.cs` — `9`
- `PopupToastController.cs` — `7`
- `App.xaml.cs` — `7`

Оценка:

- это системный кодовый долг;
- часть этих `catch { }` обслуживает best-effort cleanup и защиту UI/IO;
- массово вычищать их в `3.2` опасно;
- нужен отдельный разбор на:
  - допустимые best-effort;
  - места, где нужен `DiagnosticsLog`;
  - места, где достаточно `?.` и явного null-safe поведения.

### 5.4. Массовые `MessageBox.Show`

По проекту найдено `76` вызовов `MessageBox.Show`.

Крупнейшие концентрации:

- `MainWindow.xaml.cs` — `55`
- `App.xaml.cs` — `6`
- `SettingsWindow.xaml.cs` — `4`
- `ChangePasswordWindow.xaml.cs` — `3`

Оценка:

- это не мусор;
- часть вызовов является нормой для ошибок, подтверждений и защитных сценариев;
- без отдельной инвентаризации нельзя решать, что переводить на toast, а что оставлять модальным;
- это не задача `3.2`.

## 9. Итоговая классификация для cleanup-линии

### 9.1. Что безопасно включать в `Этап 3 / Подблок 3.2`

- удалить пустую папку `analysis_frames/`;
- удалить дублирующий файл `.gitignore.txt`;

- при отдельном подтверждении обновить устаревший `README.md`.

### 9.2. Что не включать в `Этап 3 / Подблок 3.2`

- массовое вычищение `catch { }`;
- дробление `MainWindow.xaml.cs`;
- дробление `EntryWindow.xaml.cs`;
- массовый перевод `MessageBox` на toast;
- удаление `Theme.Default.xaml`;
- удаление `Theme.PipBoy.xaml`;
- перенос локальных `MainWindow` styles в baseline;
- замена остаточных `SystemColors` в info/toast механике.

### 9.3. Что логично вынести в `Этап 3 / Подблок 3.3`

- классификация и уменьшение пустых `catch { }`;
- точечный code health cleanup по `MainWindow.xaml.cs` и `EntryWindow.xaml.cs`;
- вынос безопасных helper-методов из монолитных участков;
- инвентаризация `MessageBox` по категориям: критично оставить / можно переводить / нельзя трогать.

- extraction общих UI-metrics и state-механик из `MainWindow.xaml`;
- устранение остаточных local-style exception points;
- подготовка чистой опоры для `Светлой темы`.

## 10. Вывод аудита

Проект сейчас находится в рабочем и сборочно-чистом состоянии.

Главная проблема не в сломанной сборке и не в очевидном мусоре, а в том, что:

- вокруг ядра проекта накопились локальные артефакты среды;
- документы частично разошлись по новой theme-линии;
- кодовые и UI-механики все еще слишком завязаны на монолитные зоны;
- safe cleanup и structural cleanup нельзя смешивать.

Итог:

- `Этап 3 / Подблок 3.2` должен быть коротким и безопасным cleanup-проходом;
- `Этап 3 / Подблок 3.3` — отдельным code health cleanup;
- только после этого имеет смысл переходить к единому baseline-скелету `Этапа 4`.
